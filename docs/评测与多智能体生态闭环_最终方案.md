# 智慧红娘 Agent：评测体系与多智能体生态闭环 —— 最终方案书

> 版本：v1.0
> 定位：项目深化期的总纲文档，统一「环境重建 → 虚拟世界 → 评测体系 → 多智能体生态 → 架构升级」的目标、任务、交付物与验收标准。
> 说明：本文档中的「已落地 / 原型验证 / 架构规划」三档，用于在开发与简历表达中严格区分完成度，不把规划当成果。

---

## 0. 一页纸结论（TL;DR）

- **核心痛点**：项目主链路已跑通（Onboarding → 意图 → 硬过滤 → Hybrid 召回 → 精排 → 证据化推荐），但缺少可复现的评测指标；且新电脑环境为空、无真人用户、无行为反馈，无法度量优化收益。
- **核心思路**：用 **30 个 persona 种子构建一个可控、可复现的「虚拟婚恋世界」**，再引入多智能体（求偶者 / 候选人 / 红娘 / 裁判 / 导演）让系统自发生成行为数据，从而在**没有真人**的前提下跑通「推荐 → 互动 → 反馈 → 评测 → 迭代」的完整闭环。
- **主线五阶段**：
  1. **P0 环境重建**：Mongo / ES / Chroma + 配置 + 依赖跑通。
  2. **P1 虚拟世界**：persona 补全 → 灌库 → 模拟 Onboarding → 进 ES/Chroma → 冻结快照。
  3. **P2 评测体系 v1**：先打通链路确定性指标（意图 / Slot / 硬约束 / 召回）+ 报告 + 门禁。
  4. **P3 多智能体生态**：Seeker 反馈环 → Critic 裁判 → Candidate 社交环 → 数据飞轮。
  5. **P4 架构升级**：Context Engineering、Agentic RAG、Reasoning 分级、RLVR、MCP 生态（均由 P2 评测背书收益）。
- **最终简历叙事**：一个「可度量、可复现、自我演化」的多智能体 LLM 推荐系统，用 self-play 数据飞轮解决无真实用户下的评测与冷启动问题。

## 1. 现状诊断

### 1.1 已落地能力（代码可佐证）

| 能力 | 位置 |
|---|---|
| LangGraph 多阶段工作流、条件路由、Refine 自修正循环 | `app/services/ai/workflows/recommendation/graph.py` |
| 十维画像 Extractor，线程池并行 + 单 Agent 失败隔离 | `app/services/ai/agents/profile_manager.py` |
| Onboarding 增量画像、完整度判断、状态快照 | `app/services/ai/workflows/recommendation/nodes/onboarding.py` |
| 意图识别 / 条件解析 / 硬过滤 | `nodes/intent.py`、`nodes/filter.py` |
| ES KNN + BM25 双路召回 + 应用层 RRF 融合 | `app/db/es_manager.py` |
| MBTI / 生活方式 / 兴趣启发式精排 | `nodes/ranking.py` |
| ChromaDB Evidence RAG + 证据化推荐语 / Deep Dive | `nodes/response.py`、`nodes/deep_dive.py`、`app/db/chroma_manager.py` |
| Onboarding 收尾一条龙（摘要 → ES → Chroma → 状态翻转） | `app/services/ai/workflows/user_init.py` |
| 多 LLM 工厂 + 轻量 IOC 容器 | `app/core/container.py` |
| 蒸馏数据生成脚本（persona → 模拟话术 → SFT/DPO 样本雏形） | `training/scripts/gen_distill_data.py` |
| 30 个结构化 persona 种子 | `training/seeds/persona_seeds.json` |

### 1.2 关键短板（本方案要解决的）

1. **无评测体系**：无法回答 Intent F1、Recall@K、NDCG、Groundedness、硬约束违反率、延迟/Token 等任何量化问题；改 Prompt/召回/排序后无法判断好坏。
2. **新电脑环境为空**：`config/config.yaml`、`.env`、`docker-compose.yml` 均不在仓库；Mongo/ES/Chroma 无数据。
3. **种子缺硬过滤字段**：persona 只有性格/职业/兴趣/价值观，缺 `gender / city / age / height / birthday / 学历 / mbti / smoking / drinking`。
4. **无真人、无反馈**：排序规则无标签校准，没有行为数据可训练或验证。
5. **工程可信度不足**：缺自动化测试、结构化观测、异步化（节点内仍有同步阻塞）、可复现部署。
6. **跨库一致性表述过度**：现为「带幂等容错的顺序编排」，非真正分布式事务（简历表述需收敛）。

## 2. 总体架构

### 2.1 目标蓝图

```
                    ┌────────────────────────────────────────┐
                    │        OrchestratorAgent（导演/世界引擎）  │
                    │  推进时钟 · 派发事件 · 制造摩擦 · 收日志    │
                    └────────────────────────────────────────┘
                                      │ 驱动
        ┌──────────────────┬──────────┴───────────┬──────────────────┐
        ▼                  ▼                      ▼                  ▼
 SeekerAgent        MatchmakerAgent          CandidateAgent       CriticAgent
 (30 个求偶者)      (现有 LangGraph 系统)     (30 个候选人)         (裁判/评测)
 按 persona 提      不重写，照常服务          第一人称应答/私聊     质量打分 + OOC 检测
 需求、做决策                                                       
        │                  │                      │                  │
        └──────── 行为事件 + 反馈 + 轨迹 (sim_events / feedback) ─────┘
                                      │
                    ┌─────────────────┴──────────────────┐
                    ▼                                     ▼
          评测报告 + 回归集(门禁)                  SFT / RLVR / DPO 训练样本
                    │                                     │
                    └────────── 改进 MatchmakerAgent ◄─────┘
                                      │
                          虚拟世界底座（可复现快照）
        MongoDB(业务/状态) · Elasticsearch(召回) · ChromaDB(证据) · 事件日志
```

### 2.2 三类记忆 / Context Engineering（贯穿升级）

- **Working Memory**：session_state（当前搜索条件、`last_target_person`、seen 列表）。
- **Episodic Memory**：Chroma 中对话事件。
- **Semantic Memory**：Mongo 中沉淀的结构化 profile。
- 升级方向：上下文按需加载（非全塞 Prompt）、对话压缩摘要、跨会话偏好漂移检测。

### 2.3 分层评测总表（指标体系）

| 层 | 对象 | 指标 | 标签来源 |
|---|---|---|---|
| L0 | Onboarding 画像 | 字段级 P/R/F1、幻觉率、核心维度覆盖率、平均完成轮数、终止判定准确率、重复追问率 | persona 即金标准 |
| L1 | 意图/条件解析 | Intent Macro-F1/Accuracy、Slot P/R/F1、Exact Match、**硬条件违反率(门禁)**、硬条件误加率、指代正确率 | 模板可控 + LLM Judge |
| L2 | 召回 | Recall@10/@20、MRR、NDCG@K、零结果率、Refine 触发正确率、硬约束通过率、Fallback 恢复率 | Oracle 相关性（独立于 ranker） |
| L3 | 排序 | NDCG@3、Precision@3、HitRate@3、Pairwise Accuracy、Top-3 多样性、缺失鲁棒性 | Oracle + Seeker 反馈 |
| L4 | 证据/生成 | Groundedness、Evidence Precision、**事实捏造率(门禁)**、硬条件忠实度、个性化、差异化、隐私泄露率 | 规则 + LLM Judge |
| L5 | 系统 | 各节点延迟/P95、LLM 调用次数、Token 成本、异常率/降级率 | trace 采集 |

> **评测红线**：硬事实（gender/city/age/height 命中、意图对错、零结果）用**代码断言**；语义相关性、Slot 语义、Groundedness 用 **LLM Judge(temp=0)**。Oracle 相关性**禁止复用** `ranking.py` 的打分逻辑，避免循环论证。

## 3. 阶段任务清单

### P0｜环境重建（前置，预计 0.5~1 天）

**目标**：新电脑从零跑起 Mongo / ES / Chroma + 配置 + 依赖。

任务：
- [ ] `pip install -r requirements.txt`（torch / sentence-transformers 为大头）。
- [ ] 配置 `HF_ENDPOINT=https://hf-mirror.com`，确保 embedding 模型可下载。
- [ ] Docker 起 **Mongo 单机** 与 **ES 单机**：ES 8 必须 `xpack.security.enabled=false`（代码强制 http 且无认证，见 `app/db/es_manager.py`）。
- [ ] ES 中文分词二选一：
  - v1 快速路线：分词器临时改 `standard`（BM25 中文效果略损，够跑通）。
  - 正规路线：ES 8.x + 版本严格对应的 `analysis-ik` 插件（`ik_smart`）。
- [ ] 产出 `config/config.yaml`（mongo_uri、es_url、es_index_name、chroma 路径、model_name、vector_dims 与 embedding 维度一致）。
- [ ] 产出 `.env.example`（`BAILIAN_API_KEY` / `BAILIAN_BASE_URL` / `JWT_SECRET_KEY`），模型名直接配新模型（OpenAI 兼容接口，换模型只改配置）。
- [ ] 产出 `docker-compose.yml` / `Dockerfile`（补齐 README 中缺失的一键起栈资产）。

**交付物**：可一键起栈的本地环境；`config/config.yaml`、`.env.example`、`docker-compose.yml`。
**验收**：三个存储可连接；脚本能建 ES 索引不报分词错；embedding 模型加载成功。

---

### P1｜虚拟世界构建（预计 1 天）

**目标**：30 个 persona → 完整虚拟用户 → 三库齐备 → 冻结为可复现快照。

新增 `training/scripts/build_world.py`（复用现有 DB/Agent 能力，不重写）：

1. **人设补全 `enrich_persona`**：Teacher LLM（temp=0、固定 seed、结构化 JSON）为每个 persona 补 `gender/city/age/height/birthday/学历/学校/mbti/smoking/drinking`；保证性别约 15/15（匹配为异性取向）；**故意埋冲突点**（条件达标但三观不合 / 看似匹配但兴趣相左）以制造评测区分度。
2. **落库**：复用 `MongoDBManager.insert_user_with_persona` 写 `users_basic` + `users_persona`。
3. **模拟 Onboarding**：复用 `gen_distill_data.py` 的 `simulate_user_input` 思路，persona 驱动生成 10~16 轮口语化对话。
4. **画像抽取**：`ProfileService` 十 Extractor 线程池并行抽取 → 写 `users_profile`。
5. **对话入库**：`insert_onboarding_dialogue` 写 `users_onboarding_dialogues`。
6. **收尾索引**：调用 `user_init.finalize_user_onboarding` → 自动进 ES（embedding）+ Chroma（证据）+ 状态翻转。
7. **冻结快照 `snapshot/`**：把补全后的 persona、基础字段、对话、世界元信息（seed、模型版本、prompt 版本、git_sha）导出为 JSON fixtures；评测从快照加载，保证可复现。

**规模与成本**：30 人 × 约 20~30 次 LLM 调用 ≈ 700~900 次，并行约 20~40 分钟。
**交付物**：`build_world.py`、`eval/world/snapshot/*.json`、三库数据。
**验收**：先跑 3 人冒烟，再跑 30 人；用 `test_langgraph.py` 手动问「帮我找杭州的男生」能召回且有推荐语；快照可离线加载复现。
**后续可选**：30 池偏小（Recall@20 区分度有限），后期通过 persona 微扰扩到 100~300 人。

---

### P2｜评测体系 v1（预计 2~3 天，地基，最高优先）

**目标**：一条命令产出可对比、可回归的分数报告。v1 聚焦链路确定性指标（L1/L2/L5）。

新增 `eval/` 包（不侵入业务代码）：

```
eval/
  world/         enrich_persona.py · build_world.py · snapshot.py
  cases/
    gen_queries.py    # 规则模板(金标准slot) + LLM口语化 + 多轮(refresh/deep_dive)
    gen_onboarding.py # persona 反推多轮 onboarding 对话
    golden/*.jsonl
  oracle/
    labels.py         # 从快照确定性算硬约束命中 + 独立 Oracle 相关性分
    judge.py          # LLM-as-Judge：rubric 常量 · JSON 解析重试3次 · 字段缺失兜底 · 原始输出留档
  runner/
    trace.py          # 驱动真实 container.recommendation_app，astream 采每节点 state/延迟/token
    run_eval.py
    metrics/          # intent · filter · recall · system（v1）；onboarding/ranking/generation（后续）
  report/
    report.py         # 聚合 report_<git_sha>.json + .md
    compare.py        # baseline vs candidate 对比 + 门禁判定
  configs/eval.yaml
```

- **Golden Case 契约**：`case_id / seeker_id / turns[] / expect_intent / expect_slots / hard_constraints / gold_ranking(oracle) / 场景标签(明确/模糊/指代/否定/空结果/对抗) / 难度`。
- **报告契约**：`run_id / git_sha / model / prompt_version / 各指标聚合值 / 分场景切片 / 最差用例 Top-N / Judge 置信度`。
- **消融实验**：BM25 only / Vector only / Hybrid RRF / Hybrid+Ranking 四档对比。
- **门禁**：PR 级（核心回归集，硬约束违反率必须为 0）、Nightly（全量 + 多模型）、Release（Hidden + 对抗集）。
- **复现性**：固定 seed、逻辑节点 temp=0、候选池快照、模型/prompt 版本入报告。

**Judge 防偏差**：只看原始事实（查询 + 候选 persona），不看系统打分/推荐语；0-2 分级或 pairwise；A/B 顺序随机；解析失败记 `parse_error` 单独统计不静默吞。

**交付物**：`eval/` 整套、首份评测报告、消融对比。
**验收**：同 commit 多次跑分一致；能输出 Intent Acc、硬约束违反率、Recall@K、零结果率、节点延迟/Token；人为引入一处硬条件违反能被门禁拦截。

### P3｜多智能体生态（预计 3~5 天，差异化亮点）

**目标**：无真人前提下，Agent 自发生成行为数据，跑通三个反馈环。**按环递进，先环1跑通再扩环2。**

#### 角色定义

| Agent | 人格来源 | 职责 |
|---|---|---|
| **SeekerAgent** | persona + ideal_partner | 做 onboarding、提需求、看推荐、决策「心动/一般/跳过/换一批」、发起私聊 |
| **CandidateAgent** | persona 池（被推荐方） | Deep dive 第一人称应答；牵线后与 Seeker 私聊破冰；以 persona + Chroma 证据为记忆 |
| **MatchmakerAgent** | 现有 LangGraph 系统 | 不重写，照常服务，是被评测/被训练对象 |
| **CriticAgent** | — | 评红娘质量 + 评对话真实性（OOC 检测），复用 `oracle/judge.py` |
| **OrchestratorAgent** | 脚本 + LLM | 推进虚拟时钟、派发事件、制造摩擦、收集结构化事件日志（固定 seed 可复现） |

#### 三个闭环

- **环 1｜推荐反馈环（最高优先，与 P2 同源）**
  `Seeker 提需求 → 红娘推荐 Top3 → Seeker 按内置偏好决策 → 隐式反馈标签(点击/感兴趣/拒绝) → 对比红娘排序 vs 真实偏好 → NDCG/Pairwise 标签 → 评测 + LTR 数据`。
  关键点：**偏好内置于决策**（用 persona 字段算确定性分 + LLM 仅做语言表达），保证反馈可信、可复现。
- **环 2｜社交互动环**
  `双向感兴趣 → 牵线 → Seeker↔Candidate 私聊 N 轮 → 是否有共同话题/是否约见面 → Critic 评匹配度与真实性 → 对话写回 Chroma 成为新 evidence → 成/不成回流为排序标签`。
  这是比静态相关性更强的标签：让两个 agent 真聊一次来验证排序。
- **环 3｜数据飞轮环**
  `所有互动 → sim_events 事件日志 → 好对话/好推荐为 SFT 正样本；红娘犯错为负样本+回归用例；偏好vs排序为 RLVR 可验证奖励 / DPO pairs → 定期重训或改 Prompt → 红娘变强 → 再模拟`。

#### 防跑偏（可信度四原则）

1. 偏好内置于决策，不只靠 LLM 表态（决策 temp=0，对话 temp=0.7）。
2. 注入摩擦与多样性（埋冲突 persona），避免反馈全是正面、评测无区分度。
3. **OOC 检测**：不符合人设的对话丢弃，不进训练集。
4. 可复现优先：固定 seed、世界快照化，否则无法回归。

**数据结构**：Mongo 新增 `sim_events`（actor / action / target / payload / ts / virtual_day）与 `feedback`（seeker / candidate / decision / reason / score）。
**交付物**：`sim/` 多智能体模块、环1 反馈数据集、环2 社交对话集、环3 训练样本、生态运行报告。
**验收**：环1 能产出与评测一致的偏好标签并驱动 NDCG；环2 对话通过 OOC 检测率达标；跑 3~5 个「虚拟周」产出带时间演化的数据集。

### P4｜架构与新概念升级（由 P2 评测背书，按需推进）

> 原则：每一项都必须用 P2 评测证明收益，禁止无评测的炫技。

- [ ] **Context Engineering**：三层记忆按需加载、对话压缩、偏好漂移检测（替换「Prompt Engineering」叙事）。
- [ ] **Agentic RAG**：Evidence 检索从「一次性向量搜」升级为「自主决定是否检索/检索谁/query 改写/多轮检索/证据不足则追问」；可选评估 GraphRAG（兴趣-职业-价值观-地域图谱），需评测证明有效。
- [ ] **Reasoning 分级（Test-Time Compute）**：`container` 增加 `reasoning_llm` 槽位，条件放宽决策、匹配理由、复杂指代用推理模型；抽取/意图用快模型；文案用便宜模型。
- [ ] **Trajectory Eval**：评测对象从「最终回复」升级为「Agent 轨迹」（意图是否对、是否该 refine、检索改写、工具调用次数、路径是否最优），与 LangGraph 节点 state 天然契合。
- [ ] **RLVR（替代部分 RLHF/DPO 叙事）**：用可自动验证奖励（硬约束命中、JSON 合法、事实 grounded）做 GRPO/RL，更适合无人工标注的个人项目。
- [ ] **MCP 生态 + A2A**：地理 MCP（距离/通勤，2dsphere）、约会场景 MCP；并把匹配能力封装为 MCP Server；红娘与候选人 Agent 间用 A2A 通信。
- [ ] **多模态/实时语音（产品形态）**：Realtime 语音 Onboarding、照片理解反哺兴趣/审美字段（成本中等，demo 画面感强）。

**不做（C 档，避免硬凑）**：纯 AIGC 头像贴皮、无评测支撑的重型知识图谱、端侧大模型、Web3、AGI 叙事。

---

### 贯穿任务｜工程加固（随各阶段补齐）

- [ ] 自动化测试：节点级 Mock LLM 测试、路由测试、集成测试、故障注入（替换 `test_langgraph.py` 调试脚本）。
- [ ] 结构化观测：Trace ID、节点延迟、Token、召回量、Refine 率、空结果率、Evidence 命中率；替换散落的 `print`。
- [ ] 异步化：消除 Onboarding 节点内同步 PyMongo / 同步 LLM 阻塞事件循环；线程池按并发限流。
- [ ] 一致性：跨 Mongo/ES/Chroma 用「可重试状态机 / Saga 补偿 / Outbox + 对账」替换「伪原子」表述。
- [ ] 隐私与伦理：画像授权、敏感字段分级与展示红线、数据删除三库同步、反歧视排序策略。

## 6. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| ES IK 插件版本不匹配 / 安全认证 | 建索引失败 | v1 用 standard 或关安全；compose 固定版本 |
| embedding 模型下载慢/维度不符 | ES KNN 建索引失败 | HF 镜像；vector_dims 与模型对齐校验 |
| LLM 补全字段不稳定 | 硬过滤标签不可信 | temp=0 + JSON 校验 + 快照冻结 + 人工抽查 |
| 30 候选池太小 | Recall@20 区分度低 | v1 冒烟够用；后期 persona 微扰扩 100~300 |
| Agent 自嗨 / OOC / 反馈全正面 | 数据不可用 | 偏好内置决策、埋冲突、OOC 检测丢弃、seed 固定 |
| Oracle 复用系统 ranker | 循环论证 | Oracle 独立字段/权重，禁调 ranking.py |
| Judge 自评偏差 | 语义分不可信 | 只看原始事实、pairwise、顺序随机、留档抽查 |
| 摊子铺太大 | 无法收敛 | 严格按 P0→P2→环1→环2→环3 顺序，先跑通再扩展 |

## 7. 立即可执行的第一步

1. 起 P0：补齐 `config/config.yaml`、`.env.example`、`docker-compose.yml`，跑通三存储。
